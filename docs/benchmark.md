# Benchmark: local restoration and scoring

This page covers the two local CPU steps after an image exists: FaceFusion restoration and ArcFace
scoring. It does not cover Gemini web latency, credit use, queuing, or any GPU execution provider.

The old restore logs in `.cache/` recorded pass / refuse decisions, not latency or memory. The
numbers below are from a run of `tools/smoke_local.py` on 2026-11-08 IST. They describe this machine
and one input image, not a target.

## Machine and input

| Item | Value |
|---|---|
| CPU | 11th Gen Intel Core i3-1115G4 @ 3.00 GHz |
| RAM | 15.7 GB |
| OS | Windows 11 Home, 10.0.26200 |
| Python (this repo) | 3.14.0 |
| OpenCV | 5.0.0 |
| onnxruntime | 1.30.0 |
| FaceFusion revision | `358f169` |
| FaceFusion Python | 3.12.10 |

Test image: 848 x 1264 JPEG generated by an earlier pipeline run, SHA-256
`86A99BFE35AAF09478A21E7E646840BD9DA3C536E66EEAAB38F0F6F976AD7B8F`. Pose read as frontal
(yaw ratio 0.87, nose -0.11). The image is gitignored and is not committed.

Restore settings: `inswapper_128`, pixel boost `256x256`, CPU execution provider, `box` and
`occlusion` masks, swapper weight 0.75, expression restorer factor 80 (the frontal defaults), face
enhancer off. The reference set was the five frontal photos routed from `facecard.json`.

## Measured

| Step | Wall time | Peak memory |
|---|---|---|
| FaceFusion restore, one image | 168.82 s | 3.05 GB |
| ArcFace, embed 5 reference photos | 12.88 s | 1.29 GB |
| ArcFace, raw sample inside the smoke run (includes JPEG decode) | 0.40 s | same process |
| ArcFace, restored sample inside the smoke run (includes JPEG decode) | 0.58 s | same process |

How memory was read:

- FaceFusion: sampled RSS of the FaceFusion child process tree every 100 ms. The parent repo Python
  process is excluded.
- ArcFace: the whole Python process peak working set, which includes OpenCV and onnxruntime. The
  five-reference row measures embedding only; `ArcFaceScorer` construction happens before that timer,
  so model load is not in it. The per-image rows reuse the same process.

Wall time for FaceFusion is `restore_face`'s `elapsed_sec`, which starts after the YuNet pose read
and reference routing. It includes FaceFusion startup, model load, the swap, and the expression
restorer.

Sanity values from the same run, not a quality claim: raw ArcFace 0.6523, restored 0.8768, threshold
0.60. Laplacian sharpness 274.4 raw, 174.6 restored. One image, one run.

## Reproduce

The exact command used for the numbers above, from the repo root:

```powershell
.venv\Scripts\python.exe tools\smoke_local.py `
  --target "outputs\20261021_173953_goal-pin-783485666540141702\v1_0.jpg" `
  --out ".cache\smoke\v1_0_restored.jpg"
```

On another checkout, use any frontal or three-quarter image with a visible face and the configured
reference photos:

```powershell
.venv\Scripts\python.exe tools\smoke_local.py --target <frontal.jpg>
```

The script runs no Gemini call. It prints the pose, the routed references, wall time, and memory,
and writes `<out>_metrics.json` with the same values, including `references_embed_sec`.

## Not measured yet

- Gemini prompt latency and end-to-end time from prompt to scored image.
- Batch throughput over many images.
- Warm against cold FaceFusion runs. The 168.82 s row includes model load for that process.
- GPU execution providers, other CPUs, and other operating systems.
- Any claim that restoration leaves the rest of the picture unchanged. The swap changes face pixels,
  and the pipeline's sharpness and background checks exist because of that.

Memory values are sampled or working-set figures, not allocator-level peaks.
